Fork T3 Code: come arrivano gli aggiornamenti

Chi fa cosa, cosa è manuale e cosa automatico, e che numeri di versione escono.

Caso 1: esce una nuova stable upstream

Vuoi solo stare al passo, senza modifiche nuove tue

Upstream
Pubblica v0.1.7.
→
Tu, 2 comandi
git fetch upstream --tags
git rebase v0.1.7
Le tue modifiche vengono riapplicate sopra la 0.1.7. Conflitti solo se upstream ha cambiato gli stessi file.
→
Tu, 1 comando
fork/release.sh
Build firmata della 0.1.7 e pubblicazione su essedev/t3code. Circa 5 minuti.
→
Automatico
L'app vede la 0.1.7, la scarica e si riavvia aggiornata. Come nel test.

Il fork non segue upstream da solo: finché non lanci rebase e release, la tua app resta dov'è. In futuro questo giro si può affidare a una GitHub Action, quando il rebase passa senza conflitti.

Caso 2: fai una modifica tua tra due stable

Esempio: aggiungi una funzione mentre upstream è ancora alla 0.1.7

Tu
Lavori sul branch fork e committi.
→
Tu, 1 comando
fork/release.sh
Vede che la 0.1.7 del fork è già uscita e rilascia una prerelease della successiva: 0.1.8-fork.1.
→
Automatico
L'app si aggiorna alla 0.1.8-fork.1.

Il suffisso serve perché l'updater propone solo versioni più alte di quella installata. Semver ordina 0.1.7 < 0.1.8-fork.1 < 0.1.8-fork.2 < 0.1.8, quindi quando upstream pubblica la 0.1.8 la tua app la riceve comunque.

Cosa funziona con ciascun tipo di versione

Uguale a upstream (0.1.7) Con suffisso (0.1.8-fork.1)
Uso normale dell'app, thread, provider, Connect Sì Sì
Update in-app dal tuo fork Sì Sì
Servizio in background, environment SSH, t3 update Sì No, fino alla stable successiva. Scaricano il runtime CLI da upstream per numero di versione, e la 0.1.8-fork.1 lì non esiste.
